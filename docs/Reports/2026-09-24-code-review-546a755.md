## 5. 详细发现

### F-01 — 没有可交付的独立游戏运行时（Blocker）

**证据**

- 顶层构建只组织 Engine、Editor、tests、Samples、spikes：`CMakeLists.txt:25-54`。
- presets 只有 `mac` 和 `mac-debug`：`CMakePresets.json:4-27`。
- M7 的 packager、`.baked`、Steam、云档和干净 Windows 安装回归尚未开始：`docs/EngineDesign/08-Development-Roadmap.md:21-23`。
- 路线图把 `1.0-preview` 定义在 M7 之后：`docs/EngineDesign/08-Development-Roadmap.md:163-167`。
- `Save.Flush()` 在没有编辑器 IO hook 时是 no-op：`Engine/Scripting/ScriptHost.cpp:120-127`。
- 当前 HUD 通道明确由编辑器 GameView 消费，打包 HUD 复用仍属 M8：`Engine/ECS/World.h:25-29`。

**影响**

模板只能在编辑器进程内运行，不能生成客户可安装、可更新、可上传平台商店的游戏包。

**建议**

建立独立 `GameEntry`/runtime host、资产烘焙、packager、运行时资源定位和版本化启动流程；先完成 Windows 编译与干净机安装，再谈发行。

### F-02 — 文件路径与模板生成存在数据删除风险（Critical）

**证据**

- `--gen-vs-template` 对用户给定目标无条件执行 `remove_all`：`Editor/App/EditorApp.cpp:599-607`。
- CLI 直接接受任意目录，没有空目录、仓库根或显式覆盖确认：`Editor/EditorEntry.cpp:81-82`。
- 项目名未限制为安全目录名，`../` 可使创建根越出父目录：`Editor/Assets/ProjectWizard.cpp:62-70`、`Editor/App/EditorApp.cpp:1591-1619`。
- 资产重命名和导入直接拼接 `newRelPath`/`relDest`：`Editor/Assets/AssetDatabase.cpp:469-480`、`Editor/Assets/AssetDatabase.cpp:506-515`。

**触发**

误把已有项目、源码目录或重要目录传给模板生成器；或资产/项目路径包含 `..`、绝对路径及符号链接逃逸。

**影响**

可能删除项目外数据、覆盖未索引文件，或把新项目创建到非预期位置。

**建议**

目标只允许不存在；覆盖必须显式 `--force`。统一做 canonical/weakly-canonical containment 校验，拒绝绝对路径、`..` 和符号链接逃逸。模板先写 staging，全部成功后再提交。

### F-03 — 损坏存档可触发巨额分配（Critical）

**证据**

- `Decode` 在验证剩余长度前按不可信 `count` reserve：`Engine/ECS/SaveChannel.cpp:91-99`。
- 在确认 `valLen` 不超过剩余字节前直接构造 vector：`Engine/ECS/SaveChannel.cpp:100-106`。
- 加载端无上限读完整文件：`Editor/EditorContext.cpp:635-642`。

**影响**

十余字节坏档即可声明接近 4 GiB 的 value 或超大 entry 数，引发 `length_error`、`bad_alloc`、进程终止或主机内存耗尽。

**建议**

设置总文件、总条目、key/value 字节上限；分配前用 checked arithmetic 验证 `valLen <= left`；完整解码到临时容器并拒绝重复 key/尾随垃圾后再替换现态。

### F-04 — 场景/Prefab 加载与保存缺乏事务性（High）

**证据**

- `LoadEntityTree` 不校验 schema，先创建全部实体，再逐字段容错；局部失败仍可能留下半实例：`Engine/Serialization/SceneArchive.cpp:300-319`。
- `Load` 先销毁当前场景，再创建新实体；字段类型错只告警继续，最终仍返回 true：`Engine/Serialization/SceneArchive.cpp:322-369`、`Engine/Serialization/SceneArchive.cpp:183-227`。
- 场景保存直接 `trunc` 原路径：`Editor/EditorContext.cpp:131-147`。
- Prefab Revert 先销毁旧树，再解析源 Prefab，失败无回滚：`Editor/EditorContext.cpp:501-525`。
- Save 临时文件写入后没有检查 `flush/close` 结果，Windows 上目标存在时 rename 也不能覆盖：`Editor/EditorContext.cpp:603-628`。

**影响**

坏档、磁盘满或进程中断可能把当前内存场景替换为半加载场景，或把磁盘文件截断；用户后续一次保存即可固化损坏。

**建议**

统一安全文件服务：同目录唯一临时文件、完整写入、flush/close 检查、平台原子 replace、上一代备份。Scene/Prefab 先在临时对象完整解析和验证，再交换。

### F-05 — 纹理热上传与在途帧存在 Vulkan 竞争（High）

**证据**

- 同尺寸资产热导入直接对现有纹理调用 `UploadTexture`：`Editor/Assets/AssetGpuCache.cpp:79-84`。
- 上传从 `VK_IMAGE_LAYOUT_UNDEFINED` 开始，未声明对旧 fragment read 的依赖：`Engine/Renderer/RHI.cpp:926-996`。
- `ImmediateSubmit` 的 queue wait 只等待新上传命令，不能补救此前已录制帧对旧纹理的采样：`Engine/Renderer/RHI.cpp:636-655`。

**影响**

旧帧 fragment shader 读取与新 copy write/layout transition 竞争，可能出现验证错误、错误画面、GPU hang 或 device lost。

**建议**

每个 GPU 资源记录 in-flight fence 世代；热替换等待旧资源退役，或创建新纹理并在安全点原子换槽。禁止用 `UNDEFINED` 隐式代替资源同步。

### F-06 — 默认粒子淡出写错颜色通道（High）

**证据**

- 插值把 R/B、G/A 两组打包后做无符号减法乘法：`Engine/Renderer/Particles.cpp:19-25`。
- 默认颜色正是 `0xFFFFFFFF → 0x80FFFFFF`：`Engine/Renderer/Particles.h:39`。

**独立核算**

默认白色到 50% alpha 的中点被算为 `0xBFFFFFFF`：Blue 变成 191，Green/Alpha 仍为 255，而不是只降低 Alpha。

**影响**

所有使用默认淡出的粒子都会出现颜色通道污染；性能测试不会发现，因为像素语义未断言。

**建议**

逐 RGBA 通道做有符号或浮点插值，并增加端点/中点/任意 t 的颜色 golden test。

### F-07 — 坏场景数据可进入 GPU 越界索引（High）

**证据**

- Renderable 只检查 `spriteId <= SpriteCount()`，未检查退役空洞：`Engine/Renderer/Renderable.cpp:111-140`。
- 空洞 sprite 的 atlasIndex 是 `0xFFFFFFFF`：`Engine/Renderer/Atlas.cpp:106-113`。
- `SpriteBatchKey` 可存 4-bit blend、2-bit filter：`Engine/Renderer/Renderable.h:21-28`。
- 实际管线数组只有 4 项、sampler 槽只有 2 项：`Engine/Renderer/SpriteBatcher.h:63-74`。
- Record 直接以这些字段索引数组：`Engine/Renderer/SpriteBatcher.cpp:143-147`。

**影响**

手改或损坏的场景可把 `0xFFFFFFFF` atlasIndex 送入 bindless 描述符，或以 blend=15/filter=3 读取固定数组之外，形成 GPU OOB、验证错误或 device lost。

**建议**

消费边界统一使用 `AtlasRegistry::IsValidSprite`；对序列化 enum 做白名单钳制；`Record` 再加防御性断言/错误计数，不能依赖场景编辑器保证数据合法。

### F-08 — 脚本生命周期存在两条断链（High）

#### 8.1 Awake/OnEnable 没有 native 上下文

`g_world/g_scene` 只在批量 Tick 窗口设置：`Engine/Scripting/ScriptHost.cpp:362-368`。`AttachBehaviour` 直接调用托管 Attach，未设置上下文：`Engine/Scripting/ScriptHost.cpp:375-385`。

因此 `Awake/OnEnable` 内调用组件读写、Input、Time、UI、Save、Instantiate 时，native API 会静默返回 0/no-op：`Engine/Scripting/ScriptHost.cpp:18-45`、`Engine/Scripting/ScriptHost.cpp:58-142`。

#### 8.2 C++ 销毁绕过托管 Detach

`Scene::Destroy` 只打 tag 和入队：`Engine/ECS/Scene.cpp:23-35`。战斗与投射物系统直接调用它：`Engine/Systems/Systems.cpp:596-618`、`Engine/Systems/Systems.cpp:650-656`、`Engine/Systems/Systems.cpp:793-803`。只有脚本结构命令路径会调用 `scriptsDestroyFn_`：`Engine/Scripting/ScriptHost.cpp:459-464`。

**影响**

实体已死后托管行为仍可能继续 Update/LateUpdate，OnDestroy 不执行，事件回调持有失效句柄。

**建议**

在统一销毁提交点增加脚本和层级销毁观察者；所有生命周期回调都在显式 World/Scene context 中执行，并用 RAII 清理上下文。

### F-09 — 事件订阅没有实例级释放（High）

**证据**

- `Events` 只有 Subscribe 和整表 Reset，没有 Unsubscribe/token：`Engine/Scripting/dotnet/Lemon.SDK/Events.cs:37-41`、`Engine/Scripting/dotnet/Lemon.SDK/Events.cs:89-95`。
- `Behaviours.Detach` 只从实例表移除行为，不清理其静态订阅：`Engine/Scripting/dotnet/Lemon.SDK/Behaviours.cs:156-168`。
- vs-survivor 模板在构造函数中订阅 Death、LevelUp、WaveStart：`Templates/vs-survivor/Game/PlayerBehaviour.cs:37-45`。

**影响**

反复生成/销毁、热重载或跨局残留会叠加回调；静态委托又会持有旧行为和旧 ALC，导致重复伤害、重复 HUD、内存增长和热重载清理失败。

**建议**

Subscribe 返回 subscription token；Detach/OnDisable 自动释放，或使用可随行为生命周期释放的订阅作用域。

### F-10 — PCG32 单点区间永久死循环（High）

**证据**

- C++ `span == 1` 时 `zone = (2^32 / 1) * 1` 截成 0，所有 `Next()` 都满足 `r >= zone`：`Engine/Core/Random.h:41-48`。
- C# 实现完全相同：`Engine/Scripting/dotnet/Lemon.SDK/Interop/Pcg32.cs:31-40`。

**影响**

任何用户脚本或系统调用 `Range(x, x)` 都会挂死域线程或模拟线程。

**建议**

在计算 span 前处理 `lo == hi`，并明确拒绝 `hi < lo`；增加 C++/C# 双端单点区间回归。

### F-11 — Windows 尚不具备编译闭环（High）

**证据**

- 无 Windows preset：`CMakePresets.json:4-27`。
- Editor 直接包含 `<unistd.h>`：`Editor/App/EditorApp.cpp:31`。
- 使用 GCC 专有 `__attribute__`、`__builtin_strcmp`、`__is_trivially_copyable`：`Engine/Core/Log.h:14`、`Engine/ECS/ComponentRegistry.h:149-152`、`Engine/Renderer/Renderable.h:35`。
- 脚本构建用 `popen` 拼接 shell 命令：`Editor/Assets/ProjectWizard.cpp:250-268`。
- 存档和管线缓存 rename 不能在 Windows 覆盖既有目标：`Editor/EditorContext.cpp:623-627`、`Engine/Renderer/RHI.cpp:1282-1299`。

**结论**

当前不是“补一个 win preset”即可发布；需要先完成平台 API、进程调用、宽字符路径和原子替换抽象。

### F-12 — Vulkan 兼容声明与 feature 启用链不完整（High）

**证据**

- 低于 Vulkan 1.3 时只选择 dynamic rendering 和 synchronization2 扩展：`Engine/Renderer/RHI.cpp:294-320`。
- 随后仍通过 `VkPhysicalDeviceVulkan12Features` 查询/要求 descriptor indexing 与 hostQueryReset：`Engine/Renderer/RHI.cpp:327-367`。
- 设备创建 feature 链没有为 Vulkan 1.1/1.2 补齐 descriptor indexing、host query reset 对应扩展：`Engine/Renderer/RHI.cpp:369-393`。
- 交换链硬请求 `TRANSFER_SRC` 和 OPAQUE composite alpha，不按 supported usage/alpha 能力选择：`Engine/Renderer/RHI.cpp:540-605`。

**影响**

部分 Vulkan 1.1/1.2 GPU 会被选中但设备创建失败；不支持调试拷贝或透明合成的 surface 也可能创建失败。

**建议**

二选一：明确最低 Vulkan 1.2/1.3 并拒绝更低设备；或完整实现版本化 feature/extension 链。交换链按能力交集选择 usage、alpha 和 format。

### F-13 — 回归与发布门禁不稳定（High）

**证据**

- CTest 只有三项：`tests/CMakeLists.txt:10-22`。
- 未发现实际 CI workflow。
- 编辑器回归 helper 不检查子进程退出码：`tools/editor-regression.sh:31-39`。
- `smoke-ui` 已知约 2/6 飘忽：`docs/EngineDesign/09-Testing.md:389-395`。
- anim-smoke 120 帧断言与采样次数矛盾：`Samples/anim-smoke/main.cpp:380-389`。
- 多个 benchmark 只打印 VERDICT，不把失败转成非零退出码。

**影响**

“本机某次跑绿”不能证明后续提交或干净环境可重复构建；发布分支可能在 macOS、Windows、GPU 设备上出现未覆盖回归。

**建议**

建立 macOS + Windows CI；将 validation error、benchmark 阈值、smoke 子进程退出码设为硬门；修复测试基建后至少连续 20 次无 flake；加入 ASan/UBSan/TSan 预设和依赖故障注入。

### F-14 — 暂停与确定性只覆盖 C++ 核心（Medium）

- `timeScale=0` 仍将所有系统以 dt=0 执行并递增 tick：`Engine/ECS/World.cpp:79-87`；C# Update 仍被调用。
- 卡片选择明确不进入 InputState：`Engine/ECS/World.h:51-67`。
- StateHash 只哈希注册到 C++ Scene 的组件：`Engine/ECS/StateHash.cpp:70-80`。
- 模板私有字段、RNG、Time.Scale、卡片选择和 `MathF.Cos/Sin` 不在哈希域：`Templates/vs-survivor/Game/PlayerBehaviour.cs:26-35`、`Templates/vs-survivor/Game/PlayerBehaviour.cs:102-119`。

**结论**

“C++ 金回放确定”成立；“含 C# 玩法、升级选择和暂停的整局确定回放”尚不成立。应作为产品限制明示，或扩展快照/命令协议。

### F-15 — FileWatcher 防抖会吞事件（Medium）

`ConsumeDirty()` 在 0.4 秒防抖未到时直接清标志，没有 pending 状态：`Editor/App/EditorApp.cpp:2584-2592`。在防抖窗口内发生的下一次脚本保存可能不再触发编译。

### F-16 — QualityManager 初始档参数错误（Medium）

构造器只初始化 `tier_`，`params_` 固定为 High：`Engine/Renderer/Quality.h:39-70`。`QualityManager(Low)` 会在 Low 提前返回后永久保持 High 粒子预算。

### F-17 — 模板 SDK 路径不可移植（Medium）

`Templates/vs-survivor/Game/Game.csproj:12-14` 使用本机绝对 `Lemon.SDK.dll` 路径。项目向导会重锚，但仓库模板本身不能直接复制到另一台机器编译。

## 12. 最终判定

Lemon 当前最有价值的部分不是“功能数量”，而是已经证明以下路线可行：

- C++20 + Vulkan 的 2D 高性能渲染路线成立。
- EnTT + JobSystem 能支撑万级实体。
- CoreCLR 批量桥在可接受性能内接入 C# 逻辑。
- Unity 风格 ECS 编辑器主流程不是空壳。
- vs-survivor 玩法链已经形成。

但路线成立不等于产品成熟。当前最需要做的是**停止扩功能，先把数据、脚本、GPU 生命周期和发布链做成可信赖的闭环**。完成 Gate A/B 后 Lemon 可以作为真实游戏垂直切片底座；完成 M7、跨平台 CI 和真人发行验收后，才有资格讨论生产引擎或 `1.0-preview`。
