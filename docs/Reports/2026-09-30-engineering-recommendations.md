# Lemon 引擎工程建议书

- **出具日期**：2026-09-30
- **审查基线**：`3597032` + 工作树未提交改动
- **关联文档**：[架构分析与缺陷评审报告](2026-09-30-architecture-and-defect-review.md)（下称《评审》）。本文件所有带 ✅ 或 `§N` 的引用均指向该报告的实证条目；本文件本身**不含新的实证结论**。
- **性质声明**：本文件是**观点与优先级判断**，不是缺陷清单。《评审》回答"哪里有问题、为什么"；本文件回答"接下来该做什么、什么不该做"。两者必须分开读——把观点当实证，或把实证当观点，都会误导决策。
- **结论一句话**：引擎的内核质量已高于不少商业 2D 引擎，但它还不能做出一个游戏来；**最大的风险不是那 48 条缺陷，是"最后一步"一直没走**。
- **变更声明**：只读评审，未修改任何源码。

## 1. 总判断

Lemon 当前的比例是**倒挂的**：一边是 16 步 grep 断言回归链、20 步固定管线、35 个组件的显式反射登记、孪生世界同 seed 的确定性自证；另一边是一个**还不能出包的二进制**——运行时零 PNG 解码能力（`STB_IMAGE_IMPLEMENTATION` 只存在于 `Editor/Tooling/StbImpl.cpp`，《评审》§5.4）、无 `GameEntry`（§5.3）、无 packager（§5.7）、无 CI、唯一构建预设在 macOS 上。

这不是在批评工程能力——恰恰相反，《评审》§4 记录的六个决策（零漂移纪律、只追加不重排的组件 id、属性式确定性自证、函数指针表尺寸握手、统一 64 实体块、两阶段销毁）是真本事，多数商业引擎做不到。**问题在于战场选错了**：纪律的边际收益已经过了顶，而"能跑起来的独立 demo"的边际收益还在最高点。

下面七条按此判断排序。每条含「依据 / 做法 / 收益 / 不做的代价」四节。

---

## 2. 建议

### R1 让 vs-survivor 不经过 `lemon-editor` 独立跑起来（最高优先）

**结论**：下一个周期只做这一件事。这是唯一能把项目从"引擎原型"重新归类为"引擎"的动作。

**依据**（《评审》§5）

| 项 | 实证 |
|---|---|
| §5.3 | 只有 `lemon-editor` 一个可执行体；运行时入口靠 `--project --play` / `--final` 旗标模拟（`EditorEntry.cpp:36`） |
| §5.4 | **运行时无 PNG 解码能力**，纹样全靠编辑器进程内 `AssetGpuCache` 上传 |
| §5.7 | 无 packager；且因 §5.4，缺的不只是打包脚本 |

**做法（最小面，先求"能跑"，不求"做好"）**

1. `Engine/Assets/` 新目录：接 `stb_image` 解码。stb 已在 `THIRD_PARTY.md` 登记，**只是换个 TU 编进 `lemon-engine`**，不是新依赖。
2. 定 `.baked` 格式：图集页打包 + sprite rect + GUID manifest。编辑器侧 `AtlasRegistry` 已有烘焙雏形，运行时只读不写。
3. `Engine/Entry/GameEntry.cpp` + CMake 里 `add_executable(lemon-game)`，与 `EditorEntry` 共用 `lemon-engine` 链接。
4. packager 最简形态 = 「目录拷贝 + 一个 manifest」，不要一开始就做压缩/加密/增量更新。

**收益**：一次性消掉四个未决项——运行时资产层、ADR-005 同源双入口、M7 packager 前置、以及"Play = JSON 快照双 World"这个权宜之计本身（Play 将从"运行游戏的唯一方式"降级为"编辑器特权"）。

**不做的代价**：M7 无法开工；ADR-005 永远是空头承诺；每加一个特性都继续加深"编辑器即运行时"的耦合。

**验收判据（建议照此写进计划）**：在一台从未构建过本仓的干净机器上，`lemon-game --project demo/svr-test` 跑满 60 帧，**全程零 C++ 参与**，WASD/开火/拾取/结算四屏全通，且 `git clean -xfd` 后不需要任何 `.lemon/` 缓存即可启动。

> 这条判据的价值高于功能本身：它会立刻撞出三五个你没想到的隐式假设（工作目录、绝对路径、`.lemon/` 缓存位置），这些在编辑器宿主下永远测不到。

### R2 补音频，划掉导航

**结论**：路线图里两个空目录（`Engine/Audio`、`Engine/Navigation`），该填前者、该删后者。

**依据**：`Engine/` 顶层实证为 `Components Core ECS Physics2D Platform Renderer Scripting Serialization Systems Ui`——无 `Audio/`、无 `Navigation/`。

**音频的做法**：SDL3 音频子系统已在依赖内（SDL3 3.2.14 已登记）。先做「混音器 + 2D 声位 + 事件触发点」，挂到现有 Systems 事件队列上。

> **关键纪律提示**：加音频时必须守住《评审》§4.1 的零漂移规则——任何新通道一律「World 持有 + 非 ECS + 不入 StateHash」。音频播放状态入 ECS 或不入哈希都会直接破坏"金回放零重录"，这是本项目最贵的一条纪律，值得在动手前先写一条回归断言。

**导航的判断**：对引擎自己声明的品类（吸血鬼幸存者类），**直线逼近 + 分离力就是正解**，这套你已经有了（AI 系统 + 空间哈希 + 分离力）。navmesh 对你不 target 的内容是纯粹的大成本。建议从 `08-Development-Roadmap.md` 划掉，并留一行说明"品类不需要"，免得以后的你看着愧疚。

### R3 建 CI——当前投入产出比最高的一项

**结论**：两天工作量，每个提交自动验证，精确覆盖最贵的那类缺陷。

**依据**

- 无 `.github`（`ls -a` 实证），全仓零 CI 配置。
- `CMakePresets.json` 解析实证：configurePresets 只有 `mac` / `mac-debug`。README 里"预设 `win` 待 M1 添加"至今未兑现——**唯一构建路径是 macOS，这本身是风险**。
- `tools/editor-regression.sh` 已有 16 步 grep 断言，但它是**人跑的**。

**做法**：把 16 步挂到 runner；加一个 Windows runner；`mac` / `win` 双跑。

**收益 1——精确覆盖"静默降级"类缺陷**。这是本建议最实在的理由：《评审》里 M1（键桶满静默丢渲染）、M3（描述符集耗尽回落纯色）、M4（几何池耗尽子树消失）、D1（IME 死）、D8（文档装载失败→输入永久让出）、D10（第 65 个资产起不采样）——**全都不红字、不崩溃、就是不对**。这类缺陷只靠人眼回归，漏过去是必然的。

**收益 2**：与《评审》§7.2.4（冒烟注入链从帧号锚定改为语义句柄）叠加，可把"负载抖动导致首跑红复跑绿"变成可追溯的 per-commit 历史。

### R4 冻结 UI 层，只修"会毁资产"的那几条

**结论**：UI / RmlUiBackend / 面板层是全仓质量洼地，停止给它加功能。

**依据**：《评审》11 条高 severity 里，D1、D6、D7、D8、D9 五条落在 UI/编辑器层，M3、M4 属 `RmlUiBackend` 自建资源管理。另 §3.5 判记：`RmlUiBackend` 是渲染层内唯一不受 RHI 纪律约束的区域。

**做法**：宣布冻结后只修两组——

- **毁用户资产**：D6（Play 中改磁盘源资产）、D7（JSON 未转义 → 资产永久损坏）、D8（装载失败不回滚 → 输入永久让出）、M23/M24/M25（改名态未复位 / 返回值被弃 / 集面无 dirty）
- **静默降级**：M3（描述符集耗尽回落平色）、M4（几何池耗尽子树消失）、D9（外部纹view 无失效路径）

`RtUi` 兼容层按既定计划在 M8 退掉——少一条 UI 路径少一份心智负担，宜早不宜迟。

**不做的代价**：在质量洼地里继续挖，每加一个 UI 特性都在给后续所有回归添负担。

### R5 把 `demo/` 放进版本控制

**结论**：至少一小时工作量，但它是"验收判据有没有归属"的问题。

**依据**：`.gitignore:26` = `demo/`、`:36` = `ats/`、`:37` = `etest/`。而 M6a 验收①的判据是"**用户幸存者项目全流程零 C++ 可玩**"——**被验收对象本身不在版本控制内**。

**做法**：把 `demo/` 纳入 git；ignore 生成产物与中间态，**不要 ignore 源码**。`ats/`、`etest/` 可维持本地定位，但应在文档中明说它们"不承载验收判据"，否则回归基线的归属始终模糊。

**收益**：①回归基线有家可归；②R3 的 CI 有了被测对象；③你自己的测试材料不会丢。

---

### R6 三线程先别开

**结论**：模拟/渲染分线程是《评审》§7.1.1 判定的"最大性能杠杆"，但现在不要实现它。

**依据**：§5.2 实证单主线程串行跑完一切；§7.1.1 指出分线程的**前置条件是先修 D4**（UI 事件在 native 线程就地执行，绕过域线程）。

**判断**：你的目标内容规模下单线程够用——M0 spike 实测是 50 万精灵 137fps。现在分线程 = 付并发成本 + 必须先修 D4，却换不来一个可测量的收益。

**做法**：在 `01-Architecture-Overview.md` 里保留为"目标架构"，《评审》§5.2 已记录它是设计文档与代码的最大分叉，这个分叉是**有意保留的**，不是债务。等有了真游戏、有了 profiler 数据、且 D4 已修，再动手。

> 注意别把 §7.1.1 从设计文档删掉——它仍是正确的长期架构，只是**时机未到**。

---

### R7 把 01 文档改成"现状 / 目标"两栏

**结论**：对单人维护者，这是长期最贵的一笔账。

**依据**：《评审》§5 记录了 8 条设计文档与代码的实质分叉（五个不存在的目录、三线程 vs 单线程、无 GameEntry、零 PNG 解码、`After()` 零使用、alpha 强制 1、无 packager、RtUi 残留）。

**做法**：把每条分叉在 `01-Architecture-Overview.md` 里就地标注（"现状 = X，目标 = Y，分叉原因见 ……"），而不是整篇重写。重写会丢失"当初为什么这么定"的信息，而那条信息才是两年后的你真正需要的。

## 3. 节奏建议

| 阶段 | 内容 | 说明 |
|---|---|---|
| **第一个 30 天** | R3（CI）+ R5（demo 入 git）+ **R1 最小面** | 前两项不到三天，先做完；R1 占主体，**目标是"能跑"不是"做好"** |
| **第二个 30 天** | R4（UI 冻结 + 修毁资产缺陷）+ R2（音频） | 前者止血，后者补品类必需能力 |
| **90 天后** | 带着真游戏 + profiler 数据，重新评估 §7.1.1 | 那时分线程才有依据 |
| **随时** | R7；以及 R2 中"划掉导航"那一项 | 都是几行改动，随手做掉 |

**关键顺序约束**：R1 必须在 R4 之前完成主体。理由是 R1 会暴露真实的运行时假设，而 UI 层修复在这种暴露之后会更有的放矢；反过来先修 UI 层，是在一个你可能即将改变其宿主环境的层上做工。

## 4. 关于纪律的边际收益（本文件最重要的一段）

你这套纪律——零漂移、孪生世界同 hash、组件 id 只追加不重排、字节等价快照比对——**是对的，而且已经回本了**。《评审》§4 那六个决策是真的好。

但请注意它在《评审》里已经造成的可见成本：为了守住字节等价，ADR-011 明确拒绝了 Play 期调参回灌；为了守零漂移，Tween/Fx/表格/存档全部走"World 持有 + 非 ECS"这条更长的路；为了确定性，所有自动化链（smoke/bench/final）都强制每帧一步 + alpha=1。**这些代价都是值得的**——但它们是在为"一个能回放的引擎"付费。

下一个单位的纪律，边际价值已经低于一个能跑起来的独立 demo。不是该放松标准，是该换战场：把"让游戏能跑起来"当作新的第一位纪律，其余全部为它让路。

## 5. 局限与可争议点

本文件是观点。以下几条是我可能错的地方，决策前请自行加权：

1. **R1 的排序依赖"目标是做成引擎"**。如果你的真实目标是"引擎作为产品卖给团队"，排序会变——那时更需要的是稳定性 SLA、示例工程、文档与 API 兼容承诺，而不是一个能跑的 demo。
2. **R3 的 CI 形态未确认**。未检查是否存在远端仓库；若项目不准备开源，自托管 runner（`act` / 自建 runner）的形态与 GitHub Actions 不同，工作量估算会变。
3. **R2 的音频优先级是品类判断**。若实际内容偏策略/卡牌/解谜（音频可后置），R2 应降到 R4 之后。
4. **R6 的判断依赖内容规模假设**。若目标内容实际远超 M0 spike 的压测量级（例如同屏十万级带独立动画的实体），分线程的时机应提前——但**前置条件（先修 D4）不变**。
5. **人日与阶段划分是粗估**，未经任务分解；R1 的"最小面"尤其可能在 `.baked` 格式设计上超支，建议先花两天只做格式草案与可行性验证，再决定是否全量开工。
6. **本文件不含新实证**。所有事实性引用均来自《评审》，其实证口径（12 条 ✅ 亲手复核、1 条证伪）与局限见该文件 §9。
